Virtual i.MX boot ROMs for QEMU
===============================

QEMU's i.MX machines lack the boot ROM of the real SoCs, which determines the
boot device, loads the boot image from it and starts it. Later boot stages
also rely on data and services provided by the ROM. The ``qemu_imx*_rom``
configurations build an SPL which acts as such a boot ROM. It is loaded into
the boot ROM region using QEMU's ``-bios`` option and executes in place, so
unmodified boot images can be booted like on real hardware.

=================  ===========================  =========================
Configuration      QEMU machines                Boot image location
=================  ===========================  =========================
qemu_imx8mm_rom    imx8mm-evk                   ``flash.bin`` at 33 KiB
qemu_imx8mp_rom    imx8mp-evk                   ``flash.bin`` at 32 KiB
qemu_imx53_rom     imx53-qsb, imx53-tqma53      ``u-boot.imx`` at 1 KiB
qemu_imx6q_rom     sabrelite                    ``u-boot.imx`` at 1 KiB
qemu_imx6ul_rom    mcimx6ul-evk                 ``SPL`` at 1 KiB
qemu_imx7d_rom     mcimx7d-sabre                ``u-boot.imx`` at 1 KiB
=================  ===========================  =========================

The boot device is determined from the boot configuration in SRC_SBMR. Since
boot fuses aren't emulated, the ROMs default to the SD card slot of the
respective board unless internal boot from SD/eMMC is configured: USDHC2 on
i.MX8M and i.MX6UL, USDHC3 on i.MX6Q and USDHC1 on i.MX7. QEMU's i.MX6 and i.MX7
machines configure booting from that slot, like the boot switches of the real
boards. The i.MX53 ROM tries eSDHC1 and eSDHC3 in turn, which covers the SD card
slot of the QSB as well as the eMMC of the TQMa53.

Besides loading the boot image, the ROMs provide:

* the DCD execution of the boot image (i.MX53, i.MX6, i.MX7)
* the software info structure at 0x9e8 (i.MX8M) and 0x1e8 (i.MX7)
* the ROM API at 0x980 (i.MX8MP)
* the High Assurance Boot (HAB) services at 0x900 (i.MX8M), 0x94 (i.MX53,
  i.MX6Q) and 0x100 (i.MX6UL, i.MX7)
* the silicon revision at 0x48 (i.MX53)

Building and running
--------------------

Build the ROM, e.g. for the i.MX8MP:

.. code-block:: bash

    $ make qemu_imx8mp_rom_defconfig
    $ make CROSS_COMPILE=aarch64-linux-gnu-

This creates ``imx8mp-boot.rom``. Write the boot image of the board, e.g. the
``flash.bin`` of ``imx8mp_evk_defconfig``, to an SD card image and start
QEMU:

.. code-block:: bash

    $ truncate -s 64M sd.img
    $ dd if=flash.bin of=sd.img bs=1k seek=32 conv=notrunc
    $ qemu-system-aarch64 -M imx8mp-evk -bios imx8mp-boot.rom \
        -drive if=sd,bus=1,file=sd.img,format=raw,id=sd1 \
        -serial null -serial stdio

The other machines are started accordingly. The SD card image is attached via
``-drive if=sd,index=N`` to USDHC(N + 1), e.g. ``index=2`` for the SD card slot
of the sabrelite machine, whose console is the second UART. On the
mcimx6ul-evk machine, ``u-boot-dtb.img`` additionally goes to the sector
configured by ``CONFIG_SYS_MMCSD_RAW_MODE_U_BOOT_SECTOR`` of the board.

High Assurance Boot
-------------------

The ROMs implement HAB4: they authenticate the loader before starting it, and
later boot stages can authenticate further images, e.g. SPL and U-Boot proper
(via TF-A) on i.MX8M. Only RSA keys and SHA-256 digests are supported, which
is the default of NXP's Code Signing Tool (CST). Whether the device is open or closed is
determined by the SEC_CONFIG fuse, and the Super Root Key (SRK) hash is read
from the SRK_HASH fuses. Like on real hardware, failures are recorded as HAB
events, but only enforced on closed devices.

The fuses of QEMU's i.MX machines can be backed by a file. On i.MX6, i.MX7 and
i.MX8M, the fuses are accessed via the OCOTP, and each fuse word takes four
bytes in little endian order:

=============  =================  =================  ==============  =========
SoC            Words per bank     SRK_HASH           SEC_CONFIG      File size
=============  =================  =================  ==============  =========
i.MX6Q, 6UL    8                  bank 3             bank 0, word 6  512
                                                     bit 1
i.MX7          4                  bank 6 and 7       bank 1, word 3  256
                                                     bit 25
i.MX8MM, 8MP   4                  bank 6 and 7       bank 1, word 3  1024,
                                                     bit 25          1536
=============  =================  =================  ==============  =========

So for all of them, the SRK hash generated by ``srktool`` goes to byte offset
96. E.g. on i.MX8MP, program the SRK hash and close the device by setting bit 25
of SEC_CONFIG:

.. code-block:: bash

    $ truncate -s 1536 fuses.bin   # 1024 for the i.MX8MM
    $ dd if=SRK_1_2_3_4_fuse.bin of=fuses.bin bs=1 seek=96 conv=notrunc
    $ printf '\x00\x00\x00\x02' | dd of=fuses.bin bs=1 seek=28 conv=notrunc
    $ qemu-system-aarch64 -M imx8mp-evk -bios imx8mp-boot.rom \
        -drive if=sd,bus=1,file=sd.img,format=raw,id=sd1 \
        -drive if=none,id=fuses,file=fuses.bin,format=raw \
        -global imx-ocotp.drive=fuses \
        -serial null -serial stdio

On i.MX6, close the device via byte 24 instead, i.e. with
``printf '\x02' | dd of=fuses.bin bs=1 seek=24 conv=notrunc``. The file is
attached via ``-global imx-ocotp.drive=fuses`` on all of these machines.

On i.MX53, each fuse row of the IIM takes one byte, and 32 rows form a bank.
SRK_HASH[255:248] is located in bank 1, row 1, and SRK_HASH[247:0] in bank 3,
rows 1 to 31. Bit 1 of the SEC_CONFIG fuse in bank 0, row 4 closes the device:

.. code-block:: bash

    $ truncate -s 160 fuses.bin
    $ dd if=SRK_1_2_3_4_fuse.bin of=fuses.bin bs=1 count=1 seek=33 conv=notrunc
    $ dd if=SRK_1_2_3_4_fuse.bin of=fuses.bin bs=1 skip=1 seek=97 conv=notrunc
    $ printf '\x02' | dd of=fuses.bin bs=1 seek=4 conv=notrunc
    $ qemu-system-arm -M imx53-qsb -bios imx53-boot.rom \
        -drive if=sd,bus=0,file=sd.img,format=raw,id=sd0 \
        -drive if=none,id=fuses,file=fuses.bin,format=raw \
        -global imx-iim.drive=fuses \
        -serial stdio

Here, ``SRK_1_2_3_4_fuse.bin`` holds the 32 bytes of the hash, as generated by
``srktool`` with ``--fuse_format 1``.

Images signed with the corresponding keys boot normally then, while unsigned
or tampered images are rejected. On i.MX8M, the boot image can be signed by
building the board with ``CONFIG_IMX_HAB`` and CST in ``PATH`` as described in
``doc/imx/habv4/``. On i.MX53, i.MX6 and i.MX7, the ``u-boot-dtb.imx`` of a
board built with ``CONFIG_IMX_HAB`` is signed with CST manually, as described in
``doc/imx/habv4/guides/mx6_mx7_secure_boot.txt``. For SPL based boards like the
i.MX6UL EVK, both ``SPL`` and ``u-boot-ivt.img`` are signed, see
``doc/imx/habv4/guides/mx6_mx7_spl_secure_boot.txt``. The DCD is executed before
the loader is authenticated, but the CSF covers it as part of the loaded
image. U-Boot's ``hab_status`` command reports the HAB
configuration, state and events.
